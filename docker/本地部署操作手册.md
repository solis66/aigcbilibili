## 2. 首次部署：两项前置修复（**换机器必做**）

这两项在仓库之外，`docker compose up` 不会替你做；不做的话必然失败或 OOM。

### 2.1 配镜像加速器

位置：`C:\Users\<用户名>\.docker\daemon.json`（或 Docker Desktop → Settings → Docker Engine）

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run"
  ]
}
```

> ⚠️ `安装指引.md` §1 里列的另外 3 个加速器（`dockerproxy.com`、`mirror.baidubce.com`、
> `hub-mirror.c.163.com`）**已于 2026-09-22 实测全部停服**（域名解析失败），`docker.xuanyuan.me` 超时。
> 上面两个是当时实测唯一可达的。

### 2.2 抬高 WSL2 内存上限

新建 `C:\Users\<用户名>\.wslconfig`：

```ini
[wsl2]
memory=11GB
swap=8GB
```

> 不设的话 Docker Desktop 按宿主 50% 分配 = 7.6 GiB，**连 lite 子集都跑不动**，容器会被 OOM Kill。

### 2.3 让两项生效

**必须重启 Docker Desktop**（托盘鲸鱼图标右键 → Restart，或主界面 🐞 Troubleshoot → Restart）。
验证：

```powershell
docker info | Select-String "Total Memory|Registry Mirrors"
```

期望：`Total Memory: 10.69GiB`，且 `Registry Mirrors` 列出上面两个地址。

## 3. 启动步骤

```powershell
cd C:\Users\20931\Desktop\aigcbilibili\docker

# 1) 生成可选参数文件（不生成也能跑，走 compose 内默认值）
Copy-Item .env.example .env -Force

# 2) 校验编排文件（Compose v5 下可正常解析，实测 exit 0）
docker compose config --quiet

# 3) 拉取 10 个中间件镜像（约 3.5~4.5 GB，实测 8 分钟内完成）
docker compose pull mysql redis minio minio-init rocketmq-namesrv rocketmq-broker `
    nacos elasticsearch zipkin xxl-job-admin

# 4) 构建 7 个业务镜像（6 后端 + 1 前端，实测合计约 8 分钟）
docker compose build

# 5) 启动全套 16 容器
docker compose up -d

# 6) 看状态（期望：除 minio 外全部 healthy）
docker compose ps
```

> **不要用 `docker compose pull`（不带服务名）**：它会尝试拉取本地构建的
> `aigcbilibili/*` 镜像而失败，并且**一旦某个镜像报 `denied` 就会中断整批**，
> 把其余正在下载的镜像一并标成 `Interrupted`（实测踩过）。

**低内存降级（lite 子集）**：若需给 Windows 宿主留更多内存，跳过
`nacos / elasticsearch / search / zipkin / xxl-job-admin`：

```powershell
docker compose up -d mysql redis minio minio-init rocketmq-namesrv rocketmq-broker `
    gateway notice user-center video chat frontend
```

> lite 下网关的 `route5 /search/**` 会 502 —— 这是预期行为（`search` 未启动），非故障。

### 5.1 怎么上传视频（投稿）—— 2026-09-23 端到端实测跑通

**入口**：`http://localhost:2023` → 登录 → 点右上角头像进**个人空间** → 左侧菜单「**视频投稿**」。
路由是 `/userCenter/uploadVideo/:userId`（`UserCenter.vue`），⚠️ **该菜单项只有在看自己的空间时才出现**（`permiss: upId == userId`）。

**操作步骤**（页面上就这四步）：

1. 登录（必须走验证码流程，见上一节）；
2. 点「选择文件」挑一个 **mp4**；
3. 填标题、写简介；**封面可以不传**（不传时后端会自动截首帧当封面）；
4. 点「上传」。

**上传时前端发出的请求**（无需干预，但排查时要知道）：

| 阶段 | 请求 | 说明 |
|---|---|---|
| 分片探测 | `GET /api/createCenter/uploadPart` | resumable.js 开了 `testChunks:true`，会先逐片探测是否已存在；所以后端对这个接口的 GET 返回「查询成功」**是正常的** |
| 分片上传 | `POST /api/createCenter/uploadPart` | 按 **6MB** 切片逐片传（`upLoad.vue` 的 `chunkSize`）；最后一片到达时后端把分片拼成完整对象写进 minio 的 `video` 桶，并回传 `data[0]`=落库用的对象名、`data[1]`=首帧封面 base64 |
| 落库 | `POST /api/createCenter/uploadTotal` | 写 `video` 表 + 写 `dynamic`（个人动态），然后**发 MQ** |

**上传之后的异步链路**（1~2 秒内完成，不用刷新页面）：

- `video-encode` topic → `notice` 的 `VideoEncodeConsumer` → jave+ffmpeg 取时长 / 必要时转码 / 无封面时截首帧 → 回写 `video.length`（形如 `00:03`）；
- `mysqlToEs` topic → 同步到 Elasticsearch。

**体积约束有三处，实际上限取最小者**：

| 位置 | 限制 | 备注 |
|---|---|---|
| 前端 `upLoad.vue` · `fileAdded` | 500MB | 超了只弹 `ElMessage`，**请求都不会发** |
| 后端 Spring `max-request-size` | 350MB | 权威限制 |
| nginx `client_max_body_size` | 360m | 刻意略大于后端，让后端返回 JSON 而不是 nginx 的 413 HTML 页 |

⇒ **真正能传的是 350MB 以内**（前端那个 500MB 是摆设）。又因为是 6MB 分片，**单次请求只有 6MB**，所以「文件很大」本身不会触发 413 —— 反过来，**若 nginx 那个值被改回默认 `1m`，任何视频都传不上去**（FIX-14 的头号根因）。

**上传完怎么确认**：

```powershell
# 1) 库里有记录，且 length 已被异步回写（等 1~2 秒再查）
docker exec mysql mysql -uroot -puser -N -B bilibili -e "select id,name,length,url,cover from video order by id desc limit 3;"

# 2) minio 的 video / video-cover 两个桶里都有对象
docker run --rm --network aigcbilibili_bilibili-net --entrypoint /bin/sh `
  minio/mc:RELEASE.2024-11-21T17-21-54Z `
  -c "mc alias set local http://minio:9000 minioadmin minioadmin >/dev/null && mc ls local/video && mc ls local/video-cover"

# 3) 浏览器可直接播（含 Range 点播 → 期望 206）
curl.exe -s -o NUL -w "%{http_code}" "http://localhost:2023/video/<对象名>"
```

**两个上游缺陷（不影响「传得上去」，但要知道）**：

- `uploadPart` 命中「分片已存在」的缓存分支时**不置 `hasCutImg=true`** → 前端拿不到截帧封面；
- 后端 `totalCount` 是**累加**的，同一个 `resumableIdentifier`（= `文件名-大小-时间戳`）重复上传**永远不会触发合并**。想重传同一个文件，**改个文件名**即可。

⚠️ **测试用的 mp4 必须是真视频**。手工拼出来的「头部 + 填充」文件（没有 `moov` box）会**骗过整条上传链路**（nginx 200 / 落库 / minio / Range 206 全过），只有消费者会报
`ws.schild.jave.InputFormatException: Invalid data found when processing input` —— 看起来像解码器坏了，其实是样本本身不合法。自造样本最省事的办法是借容器内 jave 自带的 ffmpeg：

```powershell
docker exec notice /tmp/jave/ffmpeg-amd64-3.3.1 -f lavfi -i testsrc=duration=3:size=640x360:rate=24 `
  -c:v libx264 -pix_fmt yuv420p -y /tmp/real.mp4
docker cp notice:/tmp/real.mp4 .\real.mp4
```

## 6. 数据库：数据存在哪、怎么查看

### 6.1 数据不在项目目录里

最容易误解的一点：项目仓库里**只有建表脚本，没有数据**。

```
docker/mysql/init/
├── 01-schema.sql     12,999 B   ← 建 22 张表
├── 02-triggers.sql    1,629 B   ← 建 7 个触发器
└── 03-xxl-job.sql     7,594 B   ← 建 xxl_job 库 8 张表
```

这三个文件**只在空数据卷首次启动时执行一次**（MySQL 镜像的 `docker-entrypoint-initdb.d` 机制）。
真实数据存在 Docker **命名卷** `aigcbilibili_mysql-data` 里，物理位置在 Docker 的 WSL 虚拟机内部，
**不在 `C:\Users\20931\Desktop\aigcbilibili\` 下面**：

| 视角 | 路径 |
|---|---|
| 容器内 | `/var/lib/mysql`（`@@datadir` 实测 `/var/lib/mysql/`） |
| Docker 引擎视角 | `/var/lib/docker/volumes/aigcbilibili_mysql-data/_data` |
| **宿主 Windows 视角** | `\\wsl.localhost\docker-desktop\mnt\docker-desktop-disk\data\docker\volumes\aigcbilibili_mysql-data\_data` |

把上面第三行粘到资源管理器地址栏（或 PowerShell 里 `cd`）即可打开，实测能看到：

```
ibdata1        79,691,776 B   ← InnoDB 共享表空间
ib_logfile0    50,331,648 B   ← redo log
ib_logfile1    50,331,648 B
bilibili/                     ← 该库全部表：*.frm（结构）/ *.ibd（数据）/ *.TRG（触发器）
xxl_job/  mysql/  sys/  performance_schema/
```

> ⚠️ **不要在这个目录里直接改 / 删 / 重命名任何文件。** 这些 `.ibd` / `.frm` 是 InnoDB 的二进制
> 内部格式，只能由 mysqld 进程读写；绕过 MySQL 动这些文件 = 库损坏。
> 该路径仅适合「确认数据确实在、看体积」，看数据内容一律用下面三种方式。
> 另外建议**不要把这个目录加进 IDE 索引**（几万个内部小文件 + 二进制，会把编辑器拖死）。

### 6.2 方式 A：容器内 mysql 客户端（推荐，零依赖）

`mysql` 容器自带客户端，`docker exec` 进去就行，宿主不用装任何东西：

```powershell
# 进交互式 SQL 控制台（Ctrl+D 或 exit 退出）
docker exec -it mysql mysql -uroot -puser bilibili

# 或者跑一条语句就退出（-N -B 让输出干净、适合复制）
docker exec mysql mysql -uroot -puser -e "show databases;"
```

常用查询（均已实测）：

```powershell
# 有哪些库 → information_schema / bilibili / mysql / performance_schema / sys / xxl_job
docker exec mysql mysql -uroot -puser -e "show databases;"

# bilibili 库有哪些表 + 行数
docker exec mysql mysql -uroot -puser -e "select table_name, table_rows from information_schema.tables where table_schema='bilibili' order by table_name;"

# 查表内容（示例：视频表）
docker exec mysql mysql -uroot -puser bilibili -e "select * from video limit 20;"

# 看建表语句
docker exec mysql mysql -uroot -puser bilibili -e "show create table video;"

# 建了多少触发器
docker exec mysql mysql -uroot -puser -e "select trigger_name, event_object_table from information_schema.triggers where trigger_schema='bilibili';"
```

> `-puser` 会顺带打印一行 `Using a password on the command line interface can be insecure`，
> 这是 mysql 客户端的常规提示，**不是错误**，无视即可（想彻底消掉就把口令写进 `~/.my.cnf`）。

### 6.3 方式 B：本机 mysql 客户端直连（已可用）

你这台机器已经装了 MySQL 客户端，且 3306 已发布到宿主，所以可以直接连：

```powershell
& "C:\developer\Mysql\bin\mysql.exe" -h 127.0.0.1 -P 3306 -uroot -puser bilibili
```

实测通过（客户端 5.7.36 连服务端 5.7.44，exit 0）。
注意**用 `127.0.0.1` 而不是 `localhost`**：后者在 Windows 上可能优先走 IPv6 或尝试本地命名管道。

### 6.4 方式 C：图形化工具（最直观）

| 项 | 值 |
|---|---|
| 主机 | `127.0.0.1` |
| 端口 | `3306` |
| 用户名 | `root` |
| 密码 | `user` |
| 默认库 | `bilibili`（`xxl_job` 也要看就别限定默认库，直接连实例） |

### 6.5 备份与两个危险动作

```powershell
# 备份：mysqldump 写入容器内文件，再拷到宿主
# （不要直接用 PowerShell 的 ">" 重定向，它会写出 UTF-16LE 破坏 SQL 文件）
docker exec mysql sh -c "mysqldump -uroot -puser --databases bilibili xxl_job --result-file=/tmp/backup.sql"
docker cp mysql:/tmp/backup.sql .\backup-$(Get-Date -Format yyyyMMdd).sql
docker exec mysql rm -f /tmp/backup.sql
```

实测导出 37,940 B，文件头为 `-- MySQL dump 10.13 Distrib 5.7.44`。

| 命令 | 后果 |
|---|---|
| `docker compose down` | 只停容器，**数据保留**（日常用这个） |
| `docker compose down -v` | **删除全部命名卷** → `bilibili` / `xxl_job` 数据全没；下次 `up` 会重跑 init SQL 回到空库 |

另外 `.env` 里的 `MYSQL_ROOT_PASSWORD` **只在首次初始化空卷时生效**；卷存在之后再改它不会改库口令，
只会让后端连不上库（该键的完整说明见 `.env` 内注释）。

> 实测现状（2026-09-22 晚更新）：库**已被真实写入** —— 注册接口落库 `user` / `privilege`（实测 id 2、5），
> notice 端收到 Feign 通知并实际发射了 RocketMQ 消息。**尚未触发的**只剩视频上传/播放、私聊 WS、搜索索引（见 §10-9）。

## 7. 日常运维

```powershell
cd C:\Users\20931\Desktop\aigcbilibili\docker

docker compose ps                              # 状态
docker compose logs -f gateway                 # 跟踪某服务日志
docker compose restart video                   # 重启单服务

```

- 应用日志落宿主：`docker/logs/<service>/`，可直接用编辑器打开。
- 改外置配置：编辑 `docker/config/<service>/application*.yml` 后
  `docker compose up -d --force-recreate <service>`（无需重建镜像）。
- 改 nginx 反向代理：编辑 `docker/frontend/nginx.conf` 后执行上面那条 `nginx -s reload` **秒级生效**。
  （该文件已只读挂载进容器，改配置不必重建前端镜像；重建镜像会重跑 webpack 构建，需数分钟。）
  注意 `docker/frontend/nginx.conf` 与镜像内那份**必须保持一致**，改配置**一律改仓库文件**。

## 8. 排障速查（首次部署实际踩过的坑）

## 10. 已知限制（非故障）

1. **Nacos 实际未生效**：源码中没有任何模块引入 nacos 客户端，各 `application.yml` 里的
   `spring.cloud.nacos.discovery.*` 是被静默忽略的未知键。Nacos 容器仅为环境完整性保留，
   省掉它不造成功能退化（网关用的是显式 `uri:` 路由，不是 `lb://`）。
2. **后端无 actuator**：6 个后端都没有 `/actuator/health`，健康检查一律用 TCP 端口探活。
3. **日志目录 `module-name_IS_UNDEFINED`**：`logback-spring.xml` 的 `${module-name}` 可能解析失败，
   已知现象、不影响功能，日志照常落在 `docker/logs/<service>/`。
4. **MinIO 无 healthcheck**：其镜像基于 ubi-micro，既无 bash 也无 curl，
   任何 shell 探针都会永久 unhealthy，故刻意不加（由 `minio-init` 兜底）。
5. **Zipkin 采样率默认 0.1**：想在 Zipkin UI 看到完整链路，把 `.env` 里
   `ZIPKIN_SAMPLER_PROBABILITY` 设为 `1`。
6. **RocketMQ 客户端稳态 WARN（约 80 条/分钟）**：`docker/logs/notice/rocketmqlogs/rocketmq_client.log`
   持续输出 `doRebalance, comment-group, but the topic[comment] not exist.` 与
   `get consumer id list failed`。根因是消费者已注册订阅，但对应 topic **还没有任何生产者发送过**
   （broker 的 `autoCreateTopicEnable=true` 要等首次发送才建 topic）。**功能上良性**，
   但按 80 行/分钟约 **11 万行/天**，长期运行会撑大 `docker/logs/notice/`。
   若要消除：用 `mqadmin updateTopic` 预建 `comment / like / dynamic / video-encode` 等 topic。
7. **启动期 Zipkin 连接告警**：后端先于 Zipkin 起来时会打印
   `Check result of the [WebClientSender{http://zipkin:9411/api/v2/spans}] ... TimeoutException`。
   属启动顺序噪声，Zipkin 就绪后自行恢复。

    先查 `docker logs minio-init` 确认 `default.png` 是否播种成功、`mc anonymous set download` 是否执行。
12. **MQ 消费曾整条停摆 —— 已修（FIX-15，2026-09-23）**：症状是投稿视频**时长不显示**
    （`video.length` 恒为 NULL），但真实影响面更大 —— `video-encode-group` 与 `mysql-es-group`
    两个消费者组**自容器启动起就没消费过任何消息**（`mqadmin consumerProgress` 的 `Diff` 只涨不降，
    而 `consumerConnection` 显示消费者**在线**，故极易误判成「消费者没注册」）。
    根因**不在本项目**：`apache/rocketmq:4.9.7` 基于 `openjdk 8u372`，该版本 JDK 的 cgroup v2 探测
    在 Docker Desktop（WSL2）下抛 NPE → `ManagementFactory.getOperatingSystemMXBean()` 失败 →
    RocketMQ `StoreUtil` 类初始化永久失败 → `checkInDiskByCommitOffset`（每次拉消息必经）抛
    `NoClassDefFoundError` → **所有 Pull 请求 100% 失败**。
    处置：broker 的 `JAVA_OPT_EXT` 加 **`-XX:-UseContainerSupport`**（堆已显式锁定，关掉容器感知无风险）。
    ⚠️ 本项目其余后端用的是 `eclipse-temurin:8-jre`（**8u502**），**没有**这个 bug，故**只需改 rocketmq**。
    换机器后若又出现「消息不消费 / 时长为空」，先跑：
    `docker exec rocketmq-broker grep -c NoClassDefFoundError /home/rocketmq/logs/rocketmqlogs/remoting.log`
    —— 非 0 即本问题。
13. **「我的消息」页曾弹两条红条 —— 已修（FIX-17，2026-09-23）**：`WebSocket error出错：[object Event]`
    与 `获得点赞消息失败：接受响应后的错误：`，**是两个独立根因叠在同一页**：

    ② `notice` 里 `getCommentLikeNotice` 的 SQL `WHERE t.user_id` 引用了**不存在的别名** → 接口返 600。
    ✅ 两条报错的文案都**指不到真因**，排障时务必开浏览器 Console / 看接口原始响应：
    `onerror` 拿到的是 `Event` 对象（拼进模板串只剩 `[object Event]`）；
    而 `接受响应后的错误：` 是 `api/index.js` 响应拦截器里的**通用**兜底文案。

    把用户 id 当 comment id），详情与判据见 `README.md` §11.1 FIX-17。
14. **`/user-center/**` 这一族路径曾全部 404 —— 已修（FIX-18，2026-09-23）**：前端有 4 处按
    「`/<服务名>/<接口>`」调用（`api/video.js` 240/335/354/386 行），而网关的
    `discovery.locator`（把 `/<服务名>/**` 自动路由到该服务）**依赖 nacos 里有服务注册**，

    表现为视频详情页右侧「其它视频合集」弹 `查看视频合集中的视频失败：接受响应后的错误：`。
    ✅ 上游本意如此，前端没写错：网关 `SecurityConfig` 第 33 行白名单里明确列着 `"/user-center/**"`。

    （`Path=/user-center/**` + `StripPrefix=1` → `http://user-center:3000`）。

15. **搜索页弹「请求搜索结果的页数和文件数失败」、且搜索结果恒为空 —— 已修（FIX-19，2026-09-23）**。
    症状分三层，**每一层的接口都不报 500，只是在业务码/数据上表现异常**：
    ① 一进搜索页就弹红条，`GET /api/search/totalKeywordSearch/X` 返
       `600 Elasticsearch index_not_found_exception: no such index [video]`（ES **零索引**）；
       视频详情页右侧 `play/getCommendVideo/{videoId}` 同样 600（它内部 Feign 调 `search:8201/search/likelyVideoRecommend`）。
    ② 把索引建出来之后接口转 200，但 `total_video_num` 与结果列表**仍然恒为空**。
    ③ 新投稿的视频**搜不到**；已删除的视频**删不掉**（搜索里搜得到、点进去 404）。
    链路是：业务写库 → MQ `mysqlToEs` → `notice` 的 `MysqlToEsConsumer` 把变更写进 Redis 列表
    （`add:video` / `update:video` / `delete:video` / `add:user` / `update:user`）
    → `search` 的 **xxl-job 任务 `mysqlToEs`**（`search/handler/MysqlToEsHandler`）定时灌进 ES
    （索引名 `video` / `user`，见 `search/constant/Constant`）。
    四个独立根因（详细证据见 `README.md` §11.1 FIX-19）：
    ① **任务从未注册**。⚠️ 这里最容易误判：`xxl_job_registry` 里 `demo-service-impl`（= `search` 的
       `xxl.job.executor.appname`）**明明已注册在线**，但 `xxl_job_group` 里**没有它的分组**、
       `xxl_job_info` 只有一条停用的 `demoJobHandler` —— **「执行器注册成功」≠「有分组、有任务」**。
    ② `minScore(1.0f)` 是**绝对**分数阈值，而 ES 的 BM25 分数量级随索引规模变化：本机只有 1 条视频时
       「顺德」命中标题「顺德一日行」的 score 只有 **0.36** → 被 >1.0 的阈值全部滤掉。
       （`userPageKeywordSearch` **没有**这个阈值，所以「用户搜索」一直是好的，只有视频两条路径受影响。）
    ③ 增量文档的字段名与全量不一致：增量消息是 `name` / `user_id` / `video_length`，
       全量同步写的是 `video_name` / `author_id` / `author_name` / `length`，
       而搜索只查 `video_name` / `author_name` / `intro` ⇒ 新视频文档在 ES 里**确实存在**但搜不到。
    ④ 删除消息的 id 键名**又是第三套**：video 的 `delete()` 下发 `{…, id}`，而删除分支读 `video_id`
       ⇒ `DeleteRequest(indexName, "null")`，删的是不存在的文档。
    处置：补 `xxl_job_group` + `xxl_job_info`（等价于 admin 页面的「执行器管理→新增」「任务管理→新增」，
    `address_list` 会在 ≤30s 内自动回填）；`minScore` 参数化（**默认值 1.0 原样保留**，
    本地在 `docker/config/search/application.yml` 覆盖为 `0.1`）；`MysqlToEsHandler` 增加字段名归一化、
    update 改走 `docAsUpsert`、加空 BulkRequest 兜底、删除分支兼容两种键名。
    ⚠️ `java/search` 变了 → `docker compose build search` + `up -d --force-recreate search`。
    换机器/清库后的三行自检：

    另：`/viewCount/**`、`/search/history`、`/search/hot`、`/selfCenter/getRemotelyLikeVideo/**`

## 11. 内存限额维护规则

全套稳态实测约 **7.4 GiB / 10.69 GiB（69%）**。

首版 `mem_limit` 是**无实测数据的估算值**，真机一跑就有 **7 个容器贴顶**（最高 broker 94.6%）。
现已按「**实测占用 ≥85% 即校准**」统一处理完毕，校准后全部降到 **52%~77%**：

| 容器 | 原限额 → 校准后 | 占用率变化 |
|---|---|---|
| `rocketmq-broker` | 1024m → **1280m** | 94.6% → **76.1%** |
| `nacos` | 768m → **1024m** | 92.7% → **67.4%** |
| `xxl-job-admin` | 512m → **640m** | 92.6% → **76.1%** |
| `gateway` | 640m → **1024m** | 85.6% → **58.2%** |
| `chat` | 640m → **1024m** | 86.2% → **52.8%** |
| `search` | 768m → **1024m** | 86.5% → **58.7%** |
| `user-center` | 640m → **1024m** | 87.4% → **54.7%** |

**关键认知：`mem_limit` 是上限，不是预留。** 抬高它**不增加常驻占用**，
只留安全裕量（实测总占用在校准前后都是约 7.4 GiB，未变）。

**后续维护规则（改内存前必读）**

1. `-Xmx` 调大时，必须同步确认 **`mem_limit ≥ -Xmx × 1.5`**。当前各容器堆占限额 33%~62%。
2. 每次改动后跑 `docker stats --no-stream` 复核，**占用率应 <80%**；
   若 >85%，按同一规则再校准一次。
3. **不要只抬 `-Xmx` 不抬 `mem_limit`**：JVM 堆之外还有 metaspace、线程栈、直接内存，
   实测约占 130~200 MiB，这部分会被一起计入 cgroup。

**为什么 broker 最需要盯**：RocketMQ 用 **mmap 写 commitlog，页缓存计入 cgroup 内存统计**，
压力随消息吞吐增长；一旦触顶即 OOM Kill broker，并**连带 `notice` / `video` 因
`depends_on: service_healthy` 起不来** —— 故障半径远大于 broker 自身。
